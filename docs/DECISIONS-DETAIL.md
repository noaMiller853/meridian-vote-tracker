## 1. Ingestion rules — ING-04 to ING-13
- **Decided.** Columns are read by header name, not by position. The real files have exactly the Appendix A header, so this is a safety measure only (Excel in a right-to-left locale displays the columns reversed, which can look like a different order). A missing or unknown required header fails the whole file as a file-level error. A bad row never fails the file (ING-07).
- **Decided. CSV format is checked per line (ING-04, ING-07).** The export format has no line breaks inside a field (checked: no line in q1, rev2 or the historic file has an unbalanced quote; the longest line is 152 characters). So the file is read one physical line at a time (line number = line in the file, header = line 1) and each line is split by a small splitter that supports quoted fields and `""` escapes. A line with an unbalanced quote, a quote inside an unquoted field or text after a closing quote is **Invalid** (MalformedLine) with its raw text kept, and reading continues with the next line; a line break inside quotes is therefore just an unbalanced quote on that line. A line longer than 10,000 characters is Invalid ("line too long") and the rest of it is skipped without being held in memory. Rejected: a general CSV record reader, because one unclosed quote makes it swallow every following line into a single record (tried with CsvHelper), and it removes misplaced quotes silently (`"ab"c` became `abc`). Only an empty file or an unreadable header fails the whole file.
- **Decided.** `country_code` is normalized by trimming whitespace and upper-casing (`" fra "` -> `FRA`, real example: `deu` in q1). A harmless formatting difference must not fail the pipeline. The normalized code is used for duplicate/contradiction detection and classification.
- **Decided.** `ballot` gets the same treatment: trim and upper-case (`y` -> `Y`), then it must be exactly one of `Y`, `N`, `A`, `X` (ING-04). Anything else is invalid, including `Yes`, `YES`, `?`, `0` and an empty value (all present in the real files). Nothing is guessed: `YES` is not turned into `Y`. Source check: the assignment lists Y, N, A, X as the only valid values (ING-04, section 2, Appendix A) and never mentions words like `YES`; the mockups show YES/NO/ABSTAIN/ABSENT only as screen labels for these codes. Rejecting the words is therefore my strict reading of ING-04 and ING-06, not a sentence in the assignment, and it is consistent with ING-13 (the only fixes are trim and case). Confirmed by the owner.
- **Decided.** `resolution_title` is trimmed and every run of internal whitespace becomes one space. Nothing else in a title changes: no case change, no removal of text such as `(draft)`. Real example: q1 line 3592 (MA/2024/025) has `Nuclear  Non-Proliferation…` with two spaces; it becomes the same title as the other rows of the vote. The historic file has no such titles.
- **Decided.** Normalization is never silent (ING-13): each import report shows how many rows were normalized, with the field, the original and the normalized value. The three normalizations above (country code, ballot, title whitespace) are the only ones. A normalization is reported only when the normalized value is accepted: `Yes` becomes `YES`, which is still not a ballot, so the row is reported as Invalid with the original `Yes`, not as normalized.
- **Decided.** Nothing else is normalized. Any other bad value (unknown code, ballot outside Y/N/A/X, bad date, session that is not a positive whole number, wrong column count, empty required field, non-member on the vote date) makes the row **Invalid**. A row gets every problem listed, not only the first. A wrong column count is the only exception: the fields cannot be trusted, so it is the only reason given (real: q1 line 3139 `AGO;N`). Membership is checked on the vote date in the row itself, and only when the code is known and the date is valid.
- **Decided. Required and optional fields:** `assembly_vote_id`, `session`, `vote_date`, `resolution_title`, `country_code` and `ballot` are required. `country_name` (descriptive only, ING-11) and `published_at` (file-level, stored on `imports`) are optional, but the import report counts the rows where they are empty. In the real files every row with the right number of columns has both: 0 empty `country_name` and 0 empty `published_at` in q1 (5,896 rows), rev2 (5,960) and historic (962,171). The only rows without them have the wrong number of columns and are Invalid for that reason: q1 line 3139 (5 columns) and 11 historic rows with 7 columns (empty name, no `published_at` column; first one: line 134746).
- **Decided. Where a vote's details come from (two tiers).** (1) If the vote has at least one **valid** row, its details (session, vote_date, title) come **only from valid rows**. An Invalid row never takes part in the agreement check, so a rejected row never causes a Contradiction and never opens a vote-field conflict (ING-07: a bad row does not affect the rest of the file). (2) If the vote has **no** valid row, the details come from the **structurally valid** rows: every field has its expected form (8 columns, session, a real yyyy-mm-dd date, a title, a three-letter country code, a ballot Y/N/A/X) and the only problem is reference data (unknown code, not a member on the vote date). The vote is then created when they agree; if they disagree, nothing is created. Tier 2 only creates votes and never opens vote-field conflicts. Nothing is repaired or guessed. The vote record is created **even when none of its country rows is ingested**, but no `country_votes` row is ever created for a rejected row. Spec 7.2: vote 103 (FRA Y and N, both Contradiction, valid rows) and vote 104 (FRN unknown, NZL not a member, structurally valid) are created after the first upload, so the second upload adds FRA to them as New ("completion of a country missing in the vote"). Trade-off: a change of a vote's title (or session or date) that only Invalid rows carry is not reported as a conflict; it shows up only as Invalid rows in the report.
- **Decided. Contradiction in vote details — our interpretation:** after normalization, if the **valid** rows of one vote still disagree on session, date or title, **all** valid rows of that vote are Contradiction and only that vote is not ingested; rows that are Invalid stay Invalid. The spec says the system "does not choose a value" (ING-06) but does not say what happens to the other rows of the vote; choosing the majority would be choosing a value. The report lists each variant with its line numbers. Real example: q1 MA/2024/025, line 3593 has the title `… (draft)`; all 149 rows of the vote are Contradiction. rev2 has the vote with one title, so it arrives then as New.
- **Decided. Duplicate:** a row identical to an earlier row of the same file after normalization (same vote, details, country code and ballot; the country name is ignored, ING-11). The first one is classified, the copies are Duplicate (real: q1 MA/2024/007, three rows). If the same country has different ballots in one vote, every row of it is Contradiction, copies included (real: q1 MA/2024/012 FRA, lines 1695 Y and 1793 N).
- **Decided. What happens to an Invalid row (ING-06, ING-07, ING-14):** it is not stored in approved data, it is counted in the Invalid counter, and it is listed in the report under "Rows that were not stored" with row number, vote, country, value, outcome and reason (original value kept). All other rows of the file, including other rows of the same vote, are processed normally. The import finishes as "Completed with issues". An Invalid row never takes part in the per-country checks or in the vote-details agreement (see the two tiers above), so a single bad row cannot create a fake contradiction.
- **Decided.** Country **names** are never validated or normalized. A different name for the same code is not a conflict (ING-11) and is ignored: `countries.name` comes from the seed file, and the name as received stays in `import_rows`. The spec only says "not a conflict"; updating the name is not required, and silently overwriting reference data from a data file seemed wrong.
- **Decided (strict).** Dates must be exactly `yyyy-mm-dd` (ING-04 and Appendix A; the mockups show ISO dates too). Anything else is Invalid: `dd/mm/yyyy`, `dd-mm-yyyy`, month names, impossible dates such as 2024-02-30. Real example: q1 has 6 rows with `21/02/2024` (all in vote MA/2024/027, whose other 143 rows are ISO). They are reported as Invalid. rev2 contains the same 6 ballots in ISO, so they arrive later as New (ING-10) and the final approved data is the same as with a lenient rule. Rejected: accepting day-first formats and normalizing them (allowed by ING-13, but a deliberate deviation from the ING-04 wording, and a day/month guess is the one normalization that can change meaning). An earlier draft wrongly said the spec asks for `dd-mm-yyyy`; that format appears only in the illustrative table in section 2 of the assignment.

## 2. Country identity and membership (Decided)
- `country_code` is the key. A country is a member on date D if some membership period has `member_from <= D` and (`member_to` is empty or `D <= member_to`). Both ends are inclusive.
- A country that left and came back is **normal data**, not an anomaly: the assignment says it appears in two rows. In the real file Iceland (`ISL`) has 1995-01-01 to 2019-12-31 and 2022-01-01 to open. A vote in the gap (2020-01-01 to 2021-12-31) is not counted for ISL, and a row for ISL on such a date is Invalid ("not a member on <date>").
- Only **overlapping** periods of the same country, or `member_to` before `member_from`, are errors in the seed file.
- Real seed file: 151 rows, 150 countries, 149 rows with empty `member_to`.
- The membership table is loaded into memory once per import, not queried per row.

## 3. Reference data: countries and users (Decided)
- The system loads `seed/member_states.csv` into `countries` and `country_memberships` at startup, so `docker compose up` works on a fresh machine without a manual step. Users (Dana, Omar, Lena, `system`) are seeded too.
- The load is idempotent: it records the file hash as an import by `system` (it appears in the import history as `member_states.csv (seed)`, as in the mockups) and skips if already loaded. Otherwise it adds only missing rows and never deletes or overwrites. Overlapping periods in the file fail loudly.
- **Decided (built in step 2):** startup order is migrate (when `Database:MigrateOnStartup` is true; otherwise pending migrations stop startup), seed users, seed member states, in one transaction under an advisory lock, and a failure stops the process. It runs in `IHostedLifecycleService.StartingAsync`, before the web server accepts requests (code between `Build()` and `Run()` in `Program.cs` would be skipped by `WebApplicationFactory` in tests). A period in a changed file that overlaps one already stored stops startup too: reference data is never overwritten automatically. `imports.kind` (`Votes` or `MemberStates`) tells the seed import apart, so the history label is derived and not stored as text. One `audit_events` row per country, period and user added. If there are no countries after startup the API refuses to start: with no reference data every row of every import would be "unknown country".
- Rejected: uploading countries through the UI (the validation of every other import depends on them, and the spec wants base data with compose); countries as SQL inside a migration (hard to read and update).

## 4. History and audit trail (Decided)
- One general `audit_events` table (entity, id, action, old value, new value, actor, source import, correlation id, time) instead of a versions table per entity. It feeds the vote timeline and answers every HIS question with one query. Trade-off: JSON values are less strictly typed.
- Decision attempts that were not applied (a second analyst hitting an already resolved conflict) are logged too, because the vote timeline in the mockups shows them.
- **Decided (built in step 6). The vote timeline (HIS-04)** is the vote's audit events (VoteCreated, BallotsAdded, ConflictOpened, ConflictApproved / ConflictRejected, BallotChanged / VoteFieldChanged, DecisionAttemptRejected, PositionSet / PositionChanged) **plus one "Imported" entry per import that contained the vote**, taken from `import_votes`. Checked against the audit trail: an import that changes nothing in a vote (all rows Unchanged, Invalid rows, a conflict already pending or rejected) writes no audit event, so without `import_votes` a re-upload would be invisible in the timeline. It needs no extra audit rows and works for imports stored before this step. Each entry has time, actor, source file, previous and new value and a one-line summary. Order: time, then the Imported entry before the events of that import (its upload time comes first), then id. All these times come from the API's clock, so they compare correctly.

## 5. Conflicts and concurrency (Decided, built in step 5)
- **Who decides:** Analysts and the Admin (Lena) may approve or reject; the `system` user is refused (403). Checked in the API.
- **A decision is one transaction (CON-04, CON-05):** the conditional `UPDATE conflicts ... WHERE id = @id AND status = 'Pending'` (who, when, note), the approved-value change (Approve only) and the audit events. If the update changes 0 rows, someone else decided first: nothing is written and the answer is **409** ProblemDetails (`urn:meridian:problem:conflict-already-decided`) with who decided, when and what, and the conflict's current state in `conflict`. Nothing is overwritten silently. The losing attempt is kept in the history as `DecisionAttemptRejected` (§4), in its own transaction.
- **Approve** first locks the approved value (`SELECT ... FOR UPDATE` on the `country_votes` row or the vote), so two approvals on the same target are serialized and the value read is exactly the one replaced. The ballot gets the proposed value, the proposing import and line as its source, and the decider as `approved_by`. A vote field gets the proposed value and its own source column (`session_`, `vote_date_`, `title_source_import_id`), so approving a title does not move the source of the date (CON-02). **Reject** changes only the conflict: the approved value stays.
- **History (HIS-02, HIS-03):** `ConflictApproved` / `ConflictRejected` (old and new status, note, values) and, on Approve, `BallotChanged` or `VoteFieldChanged` with the old value and its source import and the new value and its source; actor, proposing import and correlation id on each. The conflict row itself never changes its approved or proposed value; on Approve it also stores `replaced_value` and `replaced_source_import_id`.
- **Stale conflicts (decided by the owner):** the approved value can change after a conflict was opened (another conflict on the same target was approved, or an import read the value just before a decision). `GET /api/conflicts/{id}` shows the approved value now, `isStale`, and the approval that set it. Approve on a stale conflict gives **409** (`urn:meridian:problem:conflict-stale`) and changes nothing, until it is resent with `expectedApprovedValue` equal to the current value; then the value replaced (and recorded) is the current one. A confirmed value that is no longer current is also 409. Reject is always allowed. Rejected: blocking Approve on a stale conflict for good (the re-upload would find it still pending and never open a new one, so the value could never be approved), and closing the other pending conflicts on the same target automatically (a decision nobody made).
- **Re-upload after an approval (ING-12, decided by the owner):** the value an approval replaced, coming again from a file with the same sha256 as the one that supplied it (`replaced_source_import_id`), stays a **Conflict** row with the action **AlreadySuperseded** and opens nothing. Example: file A gave FRA Y, file B's N was approved; re-uploading A proposes Y again and opens nothing. A different file proposing Y opens a new conflict, as for rejections. Counted in the report ("N already superseded") and per vote.
- The list (CON-01) shows the Pending conflicts by default; `status=Approved|Rejected|All` keeps decided ones readable with their decision (CON-06). The vote filter is the Assembly id (`MA/2024/012`), the id analysts see.
- Uniqueness is a **partial** unique index on (target, proposed value) `WHERE status = 'Pending'`. A decided conflict must not block a later real change of the same value (Y -> A -> Y -> A). Vote-field targets: `session`, `vote_date`, `title`.
- Re-upload after a rejection: the database no longer blocks it, so ingestion handles it. A row is skipped when the same proposed value was already rejected from a file with the same `sha256`. A different file proposing it again opens a new conflict.
- **Decided. Re-upload while a conflict is pending:** a row that matches an already pending conflict keeps the classification **Conflict**, exactly as on the first upload, so the class of a row never depends on how many times the file was uploaded. No second conflict is opened (ING-12). The report shows the Conflict rows and a separate line "new conflicts opened: 0 (N already waiting for a decision)". Rejected: counting such rows as Unchanged (the assignment defines Unchanged as identical to the approved data) and a separate "Already pending" class.
- Two pending conflicts on the same target with different proposed values can coexist. Approving one makes the other stale (see above).
- A vote missing from a new file is never deleted or changed (ING-09). Countries missing from an existing vote are added as New, not as conflicts (ING-10).

## 6. Scoring rules (Decided) — SNP, section 7.6
- Only `Y` and `N` count. Abstain (`A`) and absent (`X`) are not counted, neither in numerator nor denominator.
- A vote in which the country was not a member on the vote date is not counted.
- A country with no counted votes gets score `null` ("n/a"), not 0, and no rank.
- A member country with no approved ballot on a vote: not counted (shown as "no ballot", apart from absence `X`).
- **Decided (built in step 7). Votes without a position (POS-04).** The binding requirement is POS-04: such a vote never leaves a snapshot *silently*. Blocking creation comes from the example screen in Appendix B, which is not binding (it also allows "an explicit warning"). We do both: by default `POST /api/snapshots` answers 409 listing the votes without a position and creates nothing; with `excludeVotesWithoutPosition: true` the creator confirms it, and the snapshot lists those votes as excluded with the reason. The worker checks again, so a vote created by an import in between is not left out unconfirmed.
- The snapshot stores a frozen copy of position, weight and ballots at creation time, plus the rules used. The rules text is shown in every snapshot detail (spec 7.6).
- **Ranking order (Decided):** by exact score, highest first (compared as fractions, not rounded values); equal scores are ordered alphabetically by country name. Ranks are positional (1, 2, 3, ...), not shared, and shown as "N of M" where M is the number of countries that have a score. This matches the mockup (Brazil 38 and Ghana 39 with the same displayed score). The score is stored with 6 decimals and shown with one (4 of 6 = 66.7).
- **Decided. Listed countries:** every country that was a member on the date of at least one included vote; one without a counted vote is listed with n/a and no rank. A country that was never a member in the period is not listed (in 2024: New Zealand).
- **Decided. Selection (SNP-01):** a filter (date range and/or session) and a list of vote ids are a **union**: the filter's votes plus the listed ones. An unknown id is a 400 under `assemblyVoteIds`.
- **Decided. Quarter (SNP-05):** the calendar quarter of the snapshot's **latest included vote date**, set when it is saved and shown in the detail (q1 2024 → `2024-Q1`; the full history ends 2023-12-26 → `2023-Q4`). Publishing uses it: one Published snapshot per quarter, enforced by the partial unique index `ux_snapshots_published_quarter`. If the quarter has one, publish answers 409 naming it (who, when); `{"replace": true}` returns the old one to Saved and publishes the new one in one transaction, stores `replaced_snapshot_id`, and audits both (`SnapshotUnpublished`, `SnapshotPublished` with the replaced id). Two publishes at the same moment: the unique index lets one win; the other gets 409.
- **Decided. Storage of the frozen copy (SNP-04), choice (B).** `snapshot_votes` keeps one row per selected vote with its frozen details, position and weight; included votes get `ordinal` 0..n-1 (by date). `snapshot_scores` keeps one row per listed country with two strings of n characters: the frozen **ballots** (Y, N, A, X, `-` a member without a ballot, `.` not a member) and the **outcome** of each vote (M matched, D did not match, A, X, `.`, `-`). Character *i* of both belongs to the vote with ordinal *i*. Score, rank, weights and counts are stored too; nothing is recalculated when a snapshot is read, so a later change of the scoring code cannot change an old snapshot either.
  - **What we gain:** size, write speed and a truly frozen result. The full history (6,480 votes × 150 countries, about 972,000 country-vote pairs) takes **2.4 MB** per snapshot (`snapshot_scores` 0.9 MB, `snapshot_votes` 1.5 MB; the strings compress from 1.9 MB to 0.66 MB) and is written as 150 rows. The rejected one-row-per-contribution table (A) would be about 970,000 rows and an estimated 100 to 170 MB with its indexes for every full-history snapshot.
  - **What we give up:** there is no cheap query like "who voted Y on vote X in this snapshot" or "all contributions of vote X". It needs `substr(ballots, ordinal + 1, 1)` over the 150 rows of the snapshot (still small), and it cannot use an index. The per-country breakdown, which the spec asks for (SNP-03), is one row joined with the frozen vote list.
  - **If that query were needed:** add a normalized table derived from the strings for the snapshots that need it (for example published ones only), or a per-vote string per snapshot (one row per vote, one character per country), written in the same transaction. The strings stay the source.
- **Decided. Calculation (SNP-02).** A background job on the shared job table, run by its own worker so a snapshot does not wait behind an import. It is one REPEATABLE READ transaction, so it sees votes, positions, ballots and memberships as of one moment even if a decision or an import commits meanwhile. One SQL query returns a row per country with its ballots in ordinal order; memory stays small (150 rows). The job row is marked finished after the commit, because the progress writer updates it during the calculation. A restart completes a job whose snapshot was saved and fails the others. Measured on the full history (Release, local Docker PostgreSQL): **6.5 s**; the API's working set went from 301 to 311 MB during the calculation.

## 7. Import pipeline and background work (Decided, built in step 4)
- **Decided (built in step 4b). Classification in code, per vote, not in SQL.** The file is streamed line by line into a temp staging table (binary `COPY`), then read back `ORDER BY assembly_vote_id` through a server-side cursor (`FETCH 20000`), so the rows of a vote arrive together however the file is sorted (ING-03) and memory stays bounded. For each batch of complete votes, one batch query (five result sets: votes, approved ballots, pending conflicts, proposals rejected from a file with the same sha256, values an approval replaced that came from a file with the same sha256) loads the approved data; the pure Domain `RowValidator` and `VoteClassifier` decide; then `import_rows` and `import_votes` (`COPY`), votes, ballots and conflicts (`INSERT … SELECT unnest(…)`, `ON CONFLICT DO NOTHING` as a safety net) and the audit rows are written. The grouping key is the vote id, and the country code is the key inside a vote. Rejected: classification as set-based SQL, because it would duplicate the rules that are unit-tested in Domain.
- **Decided. Report (ING-14, ING-15):** counters on `imports`, a stored summary in `imports.report` (conflicts "opened N (M already waiting for a decision, K already rejected)", normalizations by field with their values, empty optional fields, votes created / in contradiction / without valid details, `published_at` and warnings), one `import_votes` row per vote ("what happened in each vote") and one `import_rows` row per line (class, reason, original value, problems, normalizations, conflict action). The API pages rows and votes (at most 500 per call); no response returns all rows of an import.
- **Measured (step 4b, Release build, local Docker PostgreSQL).** Historic file, 962,171 lines: 75 s from job start to commit, peak working set of the API process 357 MB (131 MB after start). Without the two report indexes on `import_rows`: 67 s, so they cost about 11% and are kept. A job's `finished_at` uses `clock_timestamp()`, because `now()` inside the work transaction is its start time. Step 5 added a fifth result set to the batch query (superseded values) and three source columns on `votes`: on a fresh database the historic file gives the same counts in 91.1 s, peak 348 MB, against 93.4 s for the previous code run right after it on the same machine. A first run took 139.7 s; timings on this machine vary between runs, so only back-to-back comparisons count. After step 6 (no change to the import; EF Core 9.0.21 everywhere): same counts, 69.4 s and 69.1 s on two fresh databases, peak 337 and 342 MB. On that data (6,480 votes, 962,109 country votes) `GET /api/votes?take=500` took 632 ms on its first call, the text and session filters 41 to 63 ms, one vote 73 ms and its timeline 83 ms.
- **Historic file: four mis-split lines, not title variants.** Lines 521760, 687843, 736765 and 922345 have an unquoted comma in the title (`Protection of Cultural Heritage, Including Capacity Building`) **and** no `published_at` column, so they still have exactly 8 fields, all shifted by one: the title is cut and `country_code` holds the rest of the title (` Including Capacity Building`). The title is the same as on the other ~149 rows of each vote. The first version of the classifier let these Invalid rows contribute their cut title, so each of the 4 votes became a Contradiction and 597 valid rows were not stored. With the two-tier rule above they are just 4 Invalid rows ("country_code ' Including Capacity Building' is not a member state; ballot is empty"). Re-run (same build, fresh database): 962,109 New, 30 Duplicate, 32 Invalid, 0 Contradiction, 6,480 votes created, 87.7 s, peak 352 MB (one earlier run took 286 s under load on the machine; the repeat was normal). The 4 lines were already among the 32 Invalid; of the 597 rows that were Contradiction, 596 are now New and 1 is a Duplicate.
- One import worker at a time removes races between overlapping uploads.
- **Decided. One transaction per import (step 4b):** all writes of a file (staging, `import_rows`, votes, ballots, conflicts, audit, counters and the final job status) commit together, so a failure leaves no half import. Trade-off: for the historic file (about 1M rows, about 2M inserts) the transaction runs for minutes and a failure late in the run loses that work; the file is then simply uploaded again. Progress is written on a separate autocommit connection so the UI can see it. An explicit `CommandTimeout` is set and the historic file is tested for real. Fallback if this proves too slow or fragile: one transaction per batch of about 200 votes. That is safe because a repeat upload is idempotent (already stored rows become Unchanged), but a failed import would then leave a partial import, and the report must say so. The spec does not require "no partial import"; it is our choice for simplicity.
- **Decided (step 4 plan).** Re-uploading the same file (same sha256) is always processed again, so the report reflects the current state ("0 new, N already waiting"); every upload is a separate import in the history. A job found `Running` after a restart is marked Failed ("upload the file again"), not re-queued, so a file that crashes the worker cannot crash-loop. Unknown columns in the header fail the file, like missing ones. `imports.published_at` is the single value when all valid rows agree, otherwise the latest one plus a warning in the report.
- **Decided (step 4 plan).** New ballots get `approved_by = system`: an automatic ingest is not a human approval (spec: approved data is data that was ingested or approved by a person), and `approved_by` is kept for human decisions on conflicts. The uploader stays reachable through `source_import_id`. Audit during import is one `audit_events` row per vote and import (VoteCreated, BallotsAdded, ConflictOpened) and not one per ballot (about 1M extra rows); per-value traceability (HIS-02) comes from `country_votes.source_import_id` and row number.
- **Decided (built in step 4a). Upload and worker.** The upload request streams the file into `IFileStore`, then writes the import, its queued job and an `Uploaded` audit event in one transaction and returns 202 (ING-01). The worker holds a session-level PostgreSQL advisory lock while it works, so there is one import worker across all API instances; it claims jobs with `FOR UPDATE SKIP LOCKED`, oldest first, and is woken right after an upload (5 s poll as fallback). Each job runs in one work transaction, and the job is marked Succeeded inside it; on any error the transaction rolls back and the job is marked Failed with the reason in `error` and in the import report. Only a file-level problem (empty file, missing, unknown or repeated header column) fails a file by design (ING-07). `background_jobs.phase` (Reading, Classifying, Writing) lets the UI show progress before the row total is known.
- Progress lives in a `background_jobs` table in PostgreSQL, processed by a `BackgroundService`. The UI polls every 1-2 seconds. SignalR was not chosen: persistent connections add complexity, and the database stays the source of truth anyway. It is a later upgrade.
- EF Core + Npgsql for the domain and migrations; bulk `COPY` for large files, because plain EF would be slow and memory-hungry on a million rows (**Decided**).

## 8. No AI/RAG in CSV ingestion (Decided)
- Ingestion must be deterministic, explainable per row and idempotent. Rules in code satisfy that; a language model does not.
- AI is considered only for the optional PDF bonus, and its output is treated as untrusted input.

## 9. Database design (Decided, built in step 1)
- Approved data lives in `votes`, `country_votes` and `vote_positions`. Every approved row keeps its source import and row.
- `published_at` is stored per file on `imports` (shown in the import report and conflict cards); per-row values stay in `import_rows`.
- The position column is `desired_outcome` (avoids the SQL keyword).
- Snapshot status: Calculating / Saved / Failed / Published. `quarter` is set when publishing. Un-publishing returns the snapshot to Saved with an audit event, so a second snapshot for a quarter needs an explicit un-publish.
- Enum-like columns are `text` with CHECK constraints; every foreign key is `RESTRICT`, so nothing approved is ever deleted.
- Snapshots keep frozen copies (votes with position and weight, scores, per-vote contributions), so later corrections never change a saved snapshot. Trade-off: a full-history snapshot stores about a million contribution rows.
- Full table list, relationships and constraints: `docs/DATABASE.md`.

- **Blob Storage (`dotnetcandidate2st`, container `uploads`): through configuration only; not yet verified against Azure.** `FileStore:Provider` is `Local` (default, a folder or the `meridian-uploads` volume) or `AzureBlob` (`FileStore:BlobServiceUri`, `FileStore:Container`); a wrong combination stops startup. The account has key access disabled, so there is no connection string: only Microsoft Entra auth, which needs a blob data role (for example Storage Blob Data Contributor) for the caller.
  - **Naming when the hash is known only at the end:** the upload is streamed to a temporary local file while it is hashed (memory stays at one 1 MB buffer, as in the local store), then uploaded to `{sha256}.csv` with `If-None-Match: *`. If the blob already exists (409 `BlobAlreadyExists` or 412), it is the same content, so it is stored once; the temporary file is always deleted. Cost: free disk for one upload (up to 250 MB) and the bytes are written twice. Rejected: a temporary blob plus a server-side copy (no local disk, but Copy Blob with Entra auth for the source, a copy that may not have finished, and a path Azurite cannot test).
  - **URI:** `azureblob://{container}/{sha256}.csv` in `imports.storage_uri`, not tied to the account endpoint, like `local://`. Only names the store produced can be opened. Files stored by one provider cannot be read after switching to the other; that only matters for a job still queued at the switch.
  - **Authentication:** every Azure client gets its credential from one factory. A token per resource can be set in configuration (`Azure:StorageAccessToken`, later `Azure:KeyVaultAccessToken`): a token is issued for one resource, so a storage token is never used for Key Vault. It is used as a static token, for local Docker runs where there is no `az login` (pasted from `az account get-access-token --resource https://storage.azure.com/` in Cloud Shell, about an hour, not refreshed). Without a token for that resource: `DefaultAzureCredential` (managed identity in Azure). When Azure refuses (expired token 401, missing data role 403), an upload answers 503 "File store unavailable" and the details go to the server log.
  - **Packages:** Azure.Storage.Blobs 12.30.1 and Azure.Identity 1.21.0, on Azure.Core 1.60 like the Application Insights package. Azure.Core 1.60 needs Microsoft.Extensions 10.x; the API already ran those since Application Insights, so Infrastructure now references `Microsoft.Extensions.Hosting.Abstractions` 10.0.9 to match (older Azure packages made `DefaultAzureCredential` exist twice).
  - **Tests:** Azurite (the storage emulator) with Testcontainers: save, read back, hash and length, the same file stored once, a 3 MB file, no temporary file left, foreign names refused. Azurite uses its development key, so the Entra path is covered by the credential factory tests and the live check.
- **Application Insights (`dotnetcandidate2-appi`): connected through configuration only.** `Azure.Monitor.OpenTelemetry.AspNetCore` is registered only when `APPLICATIONINSIGHTS_CONNECTION_STRING` is set and not empty (compose passes it from `.env`, empty by default; the distro would throw on an empty value). Without it nothing is registered and the API logs to the console only, as before (tested). Sampling is 100% (`SamplingRatio = 1`, rate-limited sampling off), so any request can be searched. The correlation id is a tag `CorrelationId` on the request telemetry and, through `IncludeScopes`, a property `CorrelationId` on every log written in a request or in the background job it started, so `union requests, traces | where customDimensions.CorrelationId == "<id>"` finds one request end to end. The log scopes are message templates (`CorrelationId:{CorrelationId}`), not dictionaries: a dictionary scope printed only its type name in the console, so the id never showed there before. Live check: requests and an import with `X-Correlation-Id: appi-check-1` sent on 2026-10-20 around 20:57 and 21:00 UTC; the exporter reported no send errors, and the requests and traces for `appi-check-1`, including the import worker lines, were seen in the portal.
- **Key Vault: not used.** Secrets stay in `.env` / user-secrets, never in Git.
- **Decided. Cosmos DB: not used.** The core need is relational integrity (constraints, transactions, joins over a million rows). A document store adds nothing here.

## 11. API and frontend (Proposed)
- Roles are enforced in the API (positions and publishing are Admin only), not just in the UI. One error format (ProblemDetails), documented in OpenAPI.
- **Decided (built in step 4a).** The acting user comes from the `X-User` header (the user switcher, spec section 3); every `/api` request needs a known user, otherwise 401, and the internal `system` user gets 403. `X-Correlation-Id` is taken from the UI or created, echoed in the response and in every ProblemDetails, kept in the log scope, and stored on the background job and on every audit event, so it follows an import into the worker's logs.
- **Decided (built in step 6). Who sees and sets positions:** everyone reads positions and weights; only the Admin sets them (POS-01; an Analyst gets 403). This is our interpretation of "position and weight (for the admin)" in section 6: editing is the admin's, but analysts need to see positions, because a vote without one blocks Dana's snapshot (POS-04, screen 8). Positions are not removed in this step.
- **Decided. Position changes and concurrency:** `PUT /api/votes/{id}/position {stance, weight, expectedVersion}`. Stance is For or Against (stored as `desired_outcome` Y / N), weight 1 to 5. `vote_positions.version` starts at 1 and grows by 1 on every change; the client sends the version it read, and **0 for the first position of a vote**. The current row is locked (`FOR UPDATE`); a change based on another version writes nothing and gets **409** (`urn:meridian:problem:position-changed`) with who set the current position, when, its values and version, so two admins never overwrite each other silently. A first position uses `INSERT ... ON CONFLICT DO NOTHING`, so two simultaneous first positions give one 200 and one 409 too. The write and the audit event (`PositionSet` or `PositionChanged`, previous and new stance, weight and version) are one transaction (HIS-03, POS-03). **Sending the same stance and weight again** returns 200 with `changed: false` and writes nothing: no audit event, no new version, `set_by` and `set_at` unchanged, even with an old version, because nothing would be overwritten. Rejected: `xmin` as the version (no migration, but opaque to the UI and tied to PostgreSQL internals).
- **Decided. Validation errors next to the field (POS-02), for the whole API:** errors are 400 ValidationProblemDetails under the request field name. A JSON value of the wrong type (`"weight": "abc"`, `1.5`) is reported under `weight`, not the serializer's `$.weight`, with a plain message instead of the serializer's text; a body that is not JSON is reported under `""`. Every ProblemDetails is sent as `application/problem+json`.
- The Angular client is generated from the OpenAPI contract, never handwritten.
- The mockups are guidance, not requirements; the integration between front and back is what is evaluated. Minimum: the four screens Imports, Review, Votes, Snapshots.
- **Front end (moved from DECISIONS.md).** Angular, standalone components and signals. The API client is `openapi-fetch` typed by `openapi-typescript` from the OpenAPI document (`npm run api`), so the compiler checks the contract. The browser talks to one origin (dev proxy, nginx in Docker), so no CORS is needed. Validation errors (400) show beside the field, 409 as a structured message.
